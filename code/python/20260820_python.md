# Learning Points: Incremental API Ingestion With Pagination

## Problem Summary

Implement a Python function that ingests records from a paginated API.

The function receives a fake API callable:

```python
fetch_page(cursor)
```

Each successful page returns:

```python
{
    "items": [...],
    "next_cursor": "cursor_2"
}
```

The function must:

- start from `start_cursor`
- fetch pages until `next_cursor` is `None`
- stop after `max_pages` if provided
- preserve record order
- validate response shape
- stop cleanly on API exceptions
- return records, errors, and summary cursor state

## Key Implementation Lessons

### 1. Page And Cursor Mental Model

A page is one chunk of records from an API.

Example:

```python
{
    "items": ["A", "B", "C"],
    "next_cursor": "cursor_2"
}
```

A cursor is a bookmark that tells the API where to continue.

Flow:

```text
cursor = None
fetch first page
response gives next_cursor = "cursor_2"

cursor = "cursor_2"
fetch second page
response gives next_cursor = "cursor_3"

cursor = "cursor_3"
fetch third page
response gives next_cursor = None

stop
```

Important distinction:

- `cursor`: value sent into `fetch_page`
- `next_cursor`: value returned by the API for the next request
- `last_cursor`: cursor used for the last successfully fetched page

## 2. `Callable` Means A Function Parameter

This type hint:

```python
fetch_page: Callable[[str | None], dict[str, Any]]
```

means:

> `fetch_page` is a function that accepts `str | None` and returns `dict[str, Any]`.

Example:

```python
def fake_fetch_page(cursor: str | None) -> dict[str, Any]:
    ...

result = ingest_paginated_api(fake_fetch_page)
```

Inside the ingestion function:

```python
response = fetch_page(cursor)
```

This pattern lets an interview test API-ingestion logic without making real network calls.

## 3. Check `max_pages` Before Fetching

The requirement says:

> stop after fetching at most `max_pages` pages.

So check `max_pages` before calling `fetch_page`.

Good pattern:

```python
if max_pages is not None and pages_fetched >= max_pages:
    break
```

This matters for:

```python
max_pages = 0
```

In that case, the function should fetch zero pages.

## 4. Validate Before Using The Response

This was one of the most important lessons.

Wrong order:

```python
response = fetch_page(cursor)

if response.get("next_cursor") is None:
    ...

if not isinstance(response, dict):
    ...
```

If `response` is a list or string, `.get()` crashes before validation.

Correct order:

```python
response = fetch_page(cursor)

if not isinstance(response, dict):
    errors.append(error_log(cursor, "response is not a dictionary"))
    failed = True
    break

if "items" not in response:
    errors.append(error_log(cursor, "items field is missing"))
    failed = True
    break

if not isinstance(response.get("items"), list):
    errors.append(error_log(cursor, "items must be a list"))
    failed = True
    break

if "next_cursor" not in response:
    errors.append(error_log(cursor, "next_cursor field is missing"))
    failed = True
    break
```

Rule:

> Never call dictionary methods or read fields until you know the response is a dictionary.

## 5. Exception Is Different From Bad Response Data

This was another point of confusion.

An exception means `fetch_page` crashed:

```python
try:
    response = fetch_page(cursor)
except Exception as e:
    errors.append(error_log(cursor, f"fetch_page failed: {e}"))
    failed = True
    break
```

Bad response data means `fetch_page` succeeded but returned the wrong shape:

```python
if not isinstance(response, dict):
    errors.append(error_log(cursor, "response is not a dictionary"))
    failed = True
    break
```

Use `e` only inside:

```python
except Exception as e:
```

There is no `e` during normal validation checks, because nothing crashed.

## 6. Every Failure Path Must Stop Clearly

If a response is invalid, stop ingestion immediately.

Why?

If validation fails but the loop continues, the code can:

- loop forever
- reuse the same cursor repeatedly
- try to process invalid data
- report confusing cursor state

Good failure pattern:

```python
errors.append(error_log(cursor, "items must be a list"))
failed = True
break
```

Interview phrase:

> On any API exception or invalid response shape, I stop the ingestion and return the cursor context so the job can be investigated or resumed safely.

## 7. Structured Errors Are Better Than Plain Strings

Plain string:

```python
"next_cursor doesn't exist"
```

Structured error:

```python
{
    "cursor": "cursor_2",
    "reason": "next_cursor field is missing"
}
```

Structured errors are better because they answer:

- where did it fail?
- why did it fail?
- what cursor should I inspect or retry from?

Helper:

```python
def error_log(cursor: str | None, message: str) -> dict[str, Any]:
    return {"cursor": cursor, "reason": message}
```

## 8. Cursor Tracking For Resume

Two summary fields matter:

```python
"last_cursor": ...
"next_cursor": ...
```

`last_cursor`:

> cursor used for the last successfully fetched page

`next_cursor`:

> cursor returned by the last successful response, used to resume after stopping

Example with `max_pages = 1`:

```python
fetch_page(None) -> {
    "items": [{"id": "rec_1"}],
    "next_cursor": "cursor_2"
}
```

Summary:

```python
{
    "last_cursor": None,
    "next_cursor": "cursor_2"
}
```

Meaning:

- last successful request used cursor `None`
- resume from `"cursor_2"`

## 9. `while True` With `break` Is Often Cleaner

For pagination, this is readable:

```python
while True:
    if max_pages is not None and pages_fetched >= max_pages:
        break

    response = fetch_page(cursor)

    # validate
    # process

    if next_cursor is None:
        break

    cursor = next_cursor
```

This is often simpler than managing an extra flag like:

```python
last_batch = False
```

## 10. Preserve Record Order With `extend`

When the API returns records in order and pages are fetched in order, preserve order by appending page items in sequence.

Simple pattern:

```python
records.extend(items)
records_fetched += len(items)
```

This is equivalent to:

```python
for item in items:
    records.append(item)
    records_fetched += 1
```

but shorter and clearer.

Important distinction:

```python
append(x)
```

adds `x` as one single element.

```python
extend(x)
```

adds each element inside `x`.

Example with a list:

```python
a = [1, 2]
a.append([3, 4])
# [1, 2, [3, 4]]
# nested list, length +1
```

```python
b = [1, 2]
b.extend([3, 4])
# [1, 2, 3, 4]
# unpacked, length +2
```

Summary:

| Method | What It Adds | Input Should Be | Length Change |
| --- | --- | --- | --- |
| `append(x)` | `x` as a single element | any object | always `+1` |
| `extend(x)` | every item inside `x` | an iterable such as list, tuple, string | `+len(x)` |

Be careful with strings because strings are iterable:

```python
names = ["a"]
names.append("bc")
# ["a", "bc"]
```

```python
names = ["a"]
names.extend("bc")
# ["a", "b", "c"]
```

Use `append` for one record.

Use `extend` to merge a page/list of records into the full result list.

## Testing Mental Model

For pagination/API ingestion problems, derive tests from loop stopping rules and failure paths.

Use this checklist:

1. Single page with `next_cursor = None`
2. Multiple pages until done
3. `max_pages = 1`
4. `max_pages = 0`
5. `start_cursor` is not `None`
6. Empty `items` with `next_cursor = None`
7. Empty `items` with non-null `next_cursor`
8. API exception on first page
9. API exception after successful pages
10. Response is not a dictionary
11. Missing `items`
12. `items` is not a list
13. Missing `next_cursor`
14. Summary cursor fields after partial stop
15. Error entries include cursor context

## Tests To Include In A Coding Interview

Example inline assert style:

```python
if __name__ == "__main__":
    def one_page(cursor: str | None = None) -> dict[str, Any]:
        return {
            "items": [{"id": "rec_1"}],
            "next_cursor": None,
        }

    result = ingest_paginated_api(one_page)
    assert result["records"] == [{"id": "rec_1"}]
    assert result["errors"] == []
    assert result["summary"] == {
        "pages_fetched": 1,
        "records_fetched": 1,
        "failed": False,
        "last_cursor": None,
        "next_cursor": None,
    }

    def two_pages(cursor: str | None = None) -> dict[str, Any]:
        if cursor is None:
            return {"items": [{"id": "rec_1"}], "next_cursor": "cursor_2"}
        return {"items": [{"id": "rec_2"}], "next_cursor": None}

    result = ingest_paginated_api(two_pages, max_pages=1)
    assert result["records"] == [{"id": "rec_1"}]
    assert result["summary"]["last_cursor"] is None
    assert result["summary"]["next_cursor"] == "cursor_2"

    def failing_page(cursor: str | None = None) -> dict[str, Any]:
        raise RuntimeError("boom")

    result = ingest_paginated_api(failing_page)
    assert result["summary"]["failed"] is True
    assert result["errors"] == [
        {"cursor": None, "reason": "fetch_page failed: boom"}
    ]

    print("All tests passed")
```

## Interview Explanation Pattern

A strong verbal answer:

> I treat the cursor as a resume bookmark. The function starts from `start_cursor`, fetches one page at a time, validates the response shape before using it, appends page items in order, and advances to `next_cursor`. It stops when `next_cursor` is `None`, when `max_pages` is reached, or when an API exception or invalid response occurs. On failures, I return a structured error with the cursor used for that request, and I preserve `last_cursor` and `next_cursor` so the ingestion can be investigated or resumed safely.

## Complexity

For `n` total records across `p` pages:

- Time: `O(n + p)`
- Space: `O(n + e)`, where `e` is the number of errors

The function stores all fetched records in memory for this exercise.

## Production Follow-Ups

In production, consider:

- retry with exponential backoff for transient API errors
- handling rate limits such as HTTP 429
- persisting `next_cursor` after each successful page
- storing raw API responses for audit and replay
- adding idempotent writes keyed by record ID
- logging page-level metrics: pages, records, failures, latency
- setting maximum page safety limits to avoid infinite cursor loops
- detecting repeated cursors from buggy APIs
- validating record-level schema after page-level validation
- deciding whether partial success should commit or roll back
