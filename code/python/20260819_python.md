# Learning Points: Reconcile Source And Target Extracts

## Problem Summary

Implement a Python reconciliation function for daily order-line migration checks.

The function must:

- compare source and target records by natural key `(order_id, line_id)`
- report records missing in target
- report records missing in source
- compare selected fields for mismatches
- detect duplicate keys separately in source and target
- keep the first duplicate-key record for comparison
- report only later duplicate records
- preserve input order where practical
- return summary counts

## Key Implementation Lessons

### 1. Use Tuple Keys For Natural Keys

The natural key is made from two fields:

```python
key = (record.get("order_id"), record.get("line_id"))
```

This tuple is useful because it is hashable, so it can be used in:

- `set`
- `dict` keys
- set operations like `-` and `&`

Avoid trying to use a full dictionary as a key:

```python
{"order_id": "ord_1", "line_id": "1"}
```

Dictionaries are not hashable.

## 2. Set Operators: `-` And `&`

Set operators were an important learning point in this exercise.

Given:

```python
source_keys = {
    ("ord_1001", "1"),
    ("ord_1002", "2"),
    ("ord_1005", "5"),
}

target_keys = {
    ("ord_1001", "1"),
    ("ord_1002", "2"),
    ("ord_1003", "3"),
}
```

Source-only keys:

```python
source_keys - target_keys
```

Result:

```python
{
    ("ord_1005", "5"),
}
```

These are records missing in target.

Target-only keys:

```python
target_keys - source_keys
```

Result:

```python
{
    ("ord_1003", "3"),
}
```

These are records missing in source.

Common keys:

```python
source_keys & target_keys
```

Result:

```python
{
    ("ord_1001", "1"),
    ("ord_1002", "2"),
}
```

These are records that exist on both sides and should be compared field by field.

## 3. `&` Works On Sets, Not Normal Dictionaries

This was one of the confusing points.

This works:

```python
common_keys = source_keys & target_keys
```

because both values are sets.

This does not work:

```python
common_keys = source_dict & target_dict
```

because normal dictionaries do not support `&` intersection directly.

Use dictionary key views instead:

```python
common_keys = source_dict.keys() & target_dict.keys()
```

or reuse existing key sets:

```python
common_keys = source_keys & target_keys
```

Mental model:

```python
source_dict
```

is the lookup table.

```python
source_dict.keys()
```

is the set-like view of natural keys.

## 4. Avoid `O(n * m)` Nested Comparisons

The first implementation compared every source record with every target record:

```python
for src_rec in source_records:
    for trg_rec in target_records:
        if same_key:
            compare_fields()
```

This is `O(n * m)`.

For 1,000 source records and 1,000 target records, that can mean up to 1,000,000 comparisons.

Better pattern:

```python
source_by_key = {
    (record.get("order_id"), record.get("line_id")): record
    for record in deduped_source_records
}

target_by_key = {
    (record.get("order_id"), record.get("line_id")): record
    for record in deduped_target_records
}
```

Then:

```python
common_keys = source_by_key.keys() & target_by_key.keys()

for key in common_keys:
    source_record = source_by_key[key]
    target_record = target_by_key[key]
    compare_fields()
```

This is `O(n + m)` because each side is scanned once to build dictionaries, and matching uses constant-time lookup.

## 5. Preserve Order Where It Matters

Set operations do not preserve order.

This is fine for calculating key groups:

```python
only_source_keys = source_keys - target_keys
```

But for output lists, preserve input order by iterating over original records:

```python
for record in source_records:
    key = (record.get("order_id"), record.get("line_id"))
    if key in only_source_keys:
        missing_in_target.append(record)
```

This keeps `missing_in_target` in source order.

Likewise:

```python
for record in target_records:
    key = (record.get("order_id"), record.get("line_id"))
    if key in only_target_keys:
        missing_in_source.append(record)
```

This keeps `missing_in_source` in target order.

## 6. Report Later Duplicates Only

The prompt said:

> For duplicate keys, keep the first record for comparison and report later duplicates.

So when detecting duplicates, append the duplicate immediately when it is encountered:

```python
if key in seen_keys:
    duplicate_count += 1
    duplicate_records.append(record)
else:
    seen_keys.add(key)
    deduped_records.append(record)
```

Avoid first collecting duplicated keys and then appending all records with those keys, because that includes the first record too.

The first record should be kept for comparison.

The later duplicate records should be reported separately.

## 7. Use The Variable `field`, Not The String `"field"`

This was a small but important bug.

Wrong:

```python
differences["field"] = {
    "source": source_record.get(field),
    "target": target_record.get(field),
}
```

This creates one literal key named `"field"`.

Correct:

```python
differences[field] = {
    "source": source_record.get(field),
    "target": target_record.get(field),
}
```

This uses the current field name, such as `"amount"` or `"currency"`.

## 8. Build Field Differences With A Loop

Instead of writing repeated `if` statements:

```python
if source_record.get("customer_id") != target_record.get("customer_id"):
    ...

if source_record.get("amount") != target_record.get("amount"):
    ...
```

Use a list of fields:

```python
compare_fields = ["customer_id", "amount", "currency", "updated_at"]
```

Then:

```python
differences = {}

for field in compare_fields:
    if source_record.get(field) != target_record.get(field):
        differences[field] = {
            "source": source_record.get(field),
            "target": target_record.get(field),
        }
```

This is shorter, easier to extend, and less likely to copy-paste the wrong field name.

## 9. Prefer `.get()` For Compared Fields

Using bracket access can crash if a compared field is missing:

```python
source_record[field]
```

If `field` is missing, Python raises:

```python
KeyError
```

Using `.get()` turns missing fields into `None`, allowing the mismatch report to capture the issue:

```python
differences[field] = {
    "source": source_record.get(field),
    "target": target_record.get(field),
}
```

Example:

```python
"updated_at": {
    "source": "2026-08-19T10:15:00Z",
    "target": None
}
```

## Testing Mental Model

For reconciliation problems, derive tests from each output bucket.

Use this checklist:

1. Empty source and empty target
2. One exact match
3. Source key missing in target
4. Target key missing in source
5. Same key with one field mismatch
6. Same key with multiple field mismatches
7. Duplicate key in source
8. Duplicate key in target
9. Duplicate records report only later duplicates
10. Extra fields are ignored
11. Numeric equality such as `42.5 == 42.50`
12. Compared field missing on one side
13. Summary counts match output lists

## Tests To Include In A Coding Interview

Example inline assert style:

```python
if __name__ == "__main__":
    source = {
        "order_id": "ord_1001",
        "line_id": "1",
        "customer_id": "cust_123",
        "amount": 42.50,
        "currency": "EUR",
        "updated_at": "2026-08-19T10:15:00Z",
    }

    target = source.copy()

    assert reconcile_order_lines([], [])["summary"] == {
        "source_count": 0,
        "target_count": 0,
        "matched": 0,
        "missing_in_target": 0,
        "missing_in_source": 0,
        "mismatched": 0,
        "duplicate_keys_source": 0,
        "duplicate_keys_target": 0,
    }

    result = reconcile_order_lines([source], [target])
    assert result["matched_count"] == 1
    assert result["mismatched_records"] == []

    changed_target = {
        **target,
        "amount": 40.0,
        "currency": "USD",
    }

    result = reconcile_order_lines([source], [changed_target])
    assert result["summary"]["mismatched"] == 1
    assert result["mismatched_records"][0]["differences"] == {
        "amount": {"source": 42.5, "target": 40.0},
        "currency": {"source": "EUR", "target": "USD"},
    }

    duplicate_source = {
        **source,
        "amount": 99.0,
    }

    result = reconcile_order_lines([source, duplicate_source], [target])
    assert result["summary"]["duplicate_keys_source"] == 1
    assert result["duplicate_keys"]["source"] == [duplicate_source]

    missing_field_target = target.copy()
    missing_field_target.pop("updated_at")

    result = reconcile_order_lines([source], [missing_field_target])
    assert result["mismatched_records"][0]["differences"]["updated_at"] == {
        "source": "2026-08-19T10:15:00Z",
        "target": None,
    }

    print("All tests passed")
```

## Interview Explanation Pattern

A strong verbal answer:

> I use `(order_id, line_id)` as a tuple natural key. First, I scan each extract once to build deduplicated records, key sets, and duplicate reports. Later duplicate records are reported, while the first record is kept for comparison. Then I use set difference to find keys missing on either side, preserving output order by iterating over the original inputs. For records present in both extracts, I use dictionaries keyed by the natural key so comparison is `O(n + m)` instead of nested `O(n * m)`. Field-level differences are built from a list of compared fields, and missing compared fields are represented as `None` using `.get()`.

## Complexity

For `n` source records and `m` target records:

- Time: `O(n + m)`
- Space: `O(n + m)`

The dictionaries and sets require memory proportional to the number of unique keys.

## Production Follow-Ups

In production, consider:

- validating that `order_id` and `line_id` are present before reconciliation
- deciding where malformed-key records should be reported
- using tolerances for decimal or currency comparisons if required
- using `Decimal` instead of float for money
- storing reconciliation output as metrics and detailed exception tables
- emitting counts by category: missing, mismatched, duplicate
- sampling mismatch examples in logs without exposing sensitive data
- partitioning large comparisons by business date or load batch
- pushing large-scale reconciliation into SQL or Spark when data no longer fits memory
- making reconciliation rerunnable and idempotent
