# Learning Points: Idempotent Event Deduplication

## Problem Summary

Implement a Python function that deduplicates event records before warehouse loading.

The function must:

- keep the first valid event for each `event_id`
- count identical repeated events as duplicates
- count same-`event_id` records with different content as conflicts
- exclude invalid events from deduplication
- preserve the order of first valid occurrences
- return invalid events with a reason

## Key Implementation Lessons

### 1. Use A Dictionary For Deduplication

For event deduplication, a dictionary is usually better than scanning a list.

```python
seen_events: dict[str, dict[str, Any]] = {}
```

This allows constant-time lookup by `event_id`.

Good pattern:

```python
if event_id in seen_events:
    if seen_events[event_id] != event:
        conflict_count += 1
    else:
        duplicate_count += 1
else:
    seen_events[event_id] = event
    valid_events.append(event)
```

This keeps the first valid event and compares later events against it.

### 2. Invalid Records Should Not Affect Deduplication

Validate each event before checking duplicates.

Good order:

1. Check required fields.
2. If invalid, append to `invalid_events` and `continue`.
3. Only valid events should enter `seen_events`.

This avoids incorrectly counting malformed records as duplicates or conflicts.

### 3. Avoid `not event.get(field)` For Required Fields

This is compact:

```python
if not event.get(field):
    ...
```

But it treats all falsy values as missing:

```python
None
""
"   "
0
False
[]
{}
```

Safer helper:

```python
def is_missing_required_value(value: Any) -> bool:
    return value is None or (isinstance(value, str) and value.strip() == "")
```

Then:

```python
missing_fields = [
    field
    for field in required_fields
    if field not in event or is_missing_required_value(event[field])
]
```

This catches missing, `None`, empty strings, and blank strings without accidentally rejecting valid non-string values.

### 4. Do Not Mutate Input Records When Reporting Errors

Avoid this:

```python
event["invalid_reason"] = "missing field"
```

Prefer wrapping the original record:

```python
{
    "record": event,
    "reason": "event_time"
}
```

This keeps the input data unchanged and makes the output easier to reason about.

## Testing Mental Model

When struggling to invent tests, do not start from imagination. Start from the requirements.

Use this sequence:

1. Test the output contract.
2. Test the happy path.
3. Turn each requirement into one test.
4. Add boundary cases.
5. Test counts and returned records separately when the output has multiple responsibilities.

## Tests To Include In A Coding Interview

For this problem, a strong minimum test set is:

- empty input
- single valid event
- multiple unique valid events
- identical duplicate event
- conflicting duplicate event
- missing required field
- blank required field
- invalid event with same `event_id` as a valid event

Example inline assert style:

```python
if __name__ == "__main__":
    base_event = {
        "event_id": "evt_123",
        "customer_id": "cust_1",
        "event_type": "purchase",
        "event_time": "2026-08-14T10:15:00Z",
        "payload": {"amount": 42.5, "currency": "EUR"},
    }

    assert deduplicate_events([]) == {
        "valid_events": [],
        "duplicate_count": 0,
        "conflict_count": 0,
        "invalid_events": [],
    }

    assert deduplicate_events([base_event]) == {
        "valid_events": [base_event],
        "duplicate_count": 0,
        "conflict_count": 0,
        "invalid_events": [],
    }

    result = deduplicate_events([base_event, base_event.copy()])
    assert result["valid_events"] == [base_event]
    assert result["duplicate_count"] == 1
    assert result["conflict_count"] == 0
    assert result["invalid_events"] == []

    conflicting_event = {
        **base_event,
        "payload": {"amount": 99.0, "currency": "EUR"},
    }

    result = deduplicate_events([base_event, conflicting_event])
    assert result["valid_events"] == [base_event]
    assert result["duplicate_count"] == 0
    assert result["conflict_count"] == 1
    assert result["invalid_events"] == []

    invalid_event = {
        "event_id": "evt_456",
        "customer_id": "cust_2",
        "event_type": "purchase",
    }

    result = deduplicate_events([invalid_event])
    assert result["valid_events"] == []
    assert result["duplicate_count"] == 0
    assert result["conflict_count"] == 0
    assert len(result["invalid_events"]) == 1
    assert result["invalid_events"][0]["reason"] == "event_time"

    blank_event = {**base_event, "event_id": "   "}
    result = deduplicate_events([blank_event])
    assert result["valid_events"] == []
    assert len(result["invalid_events"]) == 1
    assert result["invalid_events"][0]["reason"] == "event_id"

    print("All tests passed")
```

## Interview Explanation Pattern

A strong verbal answer:

> I validate records first because invalid records should not participate in deduplication. For valid records, I keep a dictionary keyed by `event_id` so duplicate lookup is constant time. The first valid event is retained in output order. Later records with the same ID are compared against the stored event: exact matches are counted as duplicates, while different payloads are counted as conflicts. I would test the output contract, happy path, duplicate path, conflict path, invalid records, and boundary values like blank required fields.

## Complexity

For `n` input events:

- Time: `O(n)` average case
- Space: `O(k)`, where `k` is the number of unique valid `event_id` values

## Production Follow-Ups

In production, consider:

- using an idempotent warehouse merge/upsert keyed by `event_id`
- storing raw events separately for audit and replay
- emitting metrics for valid, duplicate, conflict, and invalid counts
- logging examples of conflicts without exposing sensitive payloads
- sending malformed or conflicting records to a quarantine table or DLQ
- making deduplication state persistent if retries span multiple batches
- enforcing event schema through data contracts or CI checks
